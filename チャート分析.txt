## 手順0: 一部ノートブックの分析要否確認（他のどの手順よりも先に、必ず最初に確認する）
チャート分析の依頼を受けたら、画像の取得や経済指標の検索などの作業に入る前に、まずユーザーへ以下をYES/NO形式で確認すること。
「Claude_新高値ブレイク投資術」と「Claude_株空売り 5つの戦術」の2つのノートブックも、今回の分析対象に含めますか？（YES/NO）

- **YESの場合**: この2つも含め、対象ノートブックすべてを手順4〜5の通常フローでそれぞれ独立に並行分析する（他のノートブックと全く同じ扱いで、5-1〜5-4を個別に実行し、それぞれの結果を個別に表示する。統合や合成は行わない）。
- **NOの場合**: この2つを手順4の対象ノートブック一覧から除外し、分析を実行しない（NotebookLMへの送信回数が減るため、その分だけ回答時間を短縮できる）。それ以外の対象ノートブックは通常通り分析する。

ユーザーの回答が得られるまで手順5（NotebookLMへの送信）には進まないこと。ただし手順1〜3（データ・チャート生成、経済指標検索、ファンダメンタルズ検索）はこの質問への回答を待たずに並行して進めてよい。

## 手順1: チャート画像と価格・指標データの生成（`tools/market_data.py`、数秒で完了）
**チャート画像の添付は不要。** 銘柄（ティッカー）が分かれば、Yahoo Finance v8 APIの日足データからチャート画像とテクニカル指標値をClaude側で生成する。依頼文にも画像にもティッカーが見当たらない場合のみ、ユーザーに銘柄を尋ねる。

メイン側で、最初に次のコマンドを実行する（出力は合わせて2,500トークン程度）。
```bash
D=<スクラッチパッド>/<ティッカー>
tools/market_data.py ticker <ティッカー> "$D"     # $D/<ティッカー>_chart.png・_intraday.png・_data.txt を生成
tools/market_data.py macro "$D/macro.txt"         # 株価指数・為替・金利・逆イールド・CNN Fear & Greed Index
# 当日の相場天気予報（手順2-3のキャッシュ）。天気予報はRoutine用ブランチにしかコミットされないため、必ずそこから取り出す
git fetch -q origin claude/ecstatic-tesla-660dhs && git show "origin/claude/ecstatic-tesla-660dhs:相場天気予報/$(TZ=Asia/Tokyo date +%F).md" > "$D/weather_cache.md" 2>/dev/null || rm -f "$D/weather_cache.md"
```
- チャート画像（日足）: 直近約9ヶ月の日足（ローソク足、MA20/50/200、ボリンジャーバンド20日±2σ・±3σ、日中VWAP、出来高、MACD(12,26,9)、RSI(6,12,24)）。凡例の数値はすべて**最終日時点**の値である。
- チャート画像（5分足）: 直近2営業日の5分足と日中VWAP（日ごとにリセット）。おーちゃんのマニュアルはVWAPを「当日の日中VWAP（分足）」と定義し、VWAPへの押し込みからの反発を買い、割り込んで戻らなければ損切りとしているため（2026-09-23にノートブックへ確認済み）。
- `_data.txt`: 最終日時点の指標値（日中VWAPと終値の乖離率を含む）、直近10営業日の日足と各日の日中VWAP、チャート表示期間内の大きな値動きの日付一覧（手順3(a)の調査対象）、Yahoo銘柄ページの時価総額・実績PER・予想PER・アナリスト目標株価・決算予定日（推定値の場合はその旨）。
- 計算式はmoomooの表示値と小数第3位まで一致することを確認済み（SNDK 2026-09-09のMA・BOLL・MACD・RSI）。VWAPは5分足から算出し、moomooの売買代金÷出来高との差は0.03%だった。**なおmoomooの日足チャートに表示される「VWAP」はその日の(高値+安値+終値)÷3であり、本来のVWAPではない**（9/09は1,766.47と表示されたが、実際の日中VWAPは約1,771.8）。
- 5分足はYahooの上限により直近60日分のみ。取得できない場合、VWAPは「取得不可」と出力され、5分足画像は生成されない。
- 米国の取引時間中に実行した場合、最終日の足は「取引時間中の暫定値」と明記される。

ユーザーが画像を添付した場合も、NotebookLMへ送るのは生成したチャート画像（日足・5分足）のみとする。**moomoo等の画像上部の指標値はカーソル位置の日付の値であり、著者が過去日の値を現在値として誤読した実績がある**（2026-09-23、9/09時点のRSI80.4・MA20 1,579.45を9/22の値として判定に使った）。ユーザーが週足や自分で線を引いた画像など、日足以外の情報を含む画像を明示的に含めるよう依頼した場合のみ、生成画像に加えて追加する。

## 手順2〜3の実行方式（コンテキスト節約のため必ず守ること）

手順1の後、**WebSearchが必要な項目だけを単一のサブエージェント（Agentツール、general-purpose）に委譲すること。** メインの会話で直接WebSearchを実行してはならない。

理由: WebSearchの生の検索結果は1件あたり数千トークンあり、10件前後実行するとそれだけでメインの文脈を3万トークン以上消費する。価格・指標のようにAPIで取れる項目は手順1で取得済みなので、サブエージェントには検索でしか取れない項目だけを任せる。

サブエージェントへの指示は、`tools/データ収集指示.md` を読ませるだけでよい（指示文を毎回書き起こさない）。プロンプトには次の3点だけを書く。
- ティッカー、本日の日付（JST）、出力ディレクトリ `$D`
- 「`tools/データ収集指示.md` を読み、その通りに実行すること」
- 天気予報キャッシュ `$D/weather_cache.md` の有無（手順1で取り出せたかどうか）
- タスクA（経済指標）を省略してよいか: **同じセッション内で本日既に経済指標を取得済みなら「省略可」とし、その `econ_search.txt` を再利用する**（2銘柄目以降の分析で検索を丸ごと省ける）。それ以外は「実行」とする。

サブエージェントは結果を `$D/econ_search.txt` と `$D/fund_search.txt` に書き出し、同じ内容とチェック結果を返す。

**あわせて、このサブエージェントの起動と同時に、以下2つをメイン側で並行実行すること。** データ収集の完了を待ってから始めると、その分だけ全体の所要時間が延びる。
1. 手順4のNotebookLM認証（手順A）。認証には60秒以上かかることがある。
2. 手順5-1・5-2の画像ソース差し替え（画像は手順1で生成した `$D/<ティッカー>_chart.png` と `$D/<ティッカー>_intraday.png`）。取得データに依存しないため、データ収集の完了を待つ必要がない。

## 手順2: 経済指標・マクロ環境データ
各項目は「値・発表日（または取得日時）」を明記し、取得できなかった項目は推測で埋めず「取得不可」と明記すること。

### 手順2-1: 価格・指数データ（手順1の `market_data.py macro` で取得済み）
NYダウ、NASDAQ、SOX指数、日経平均先物（CME円建）、日経ダブルインバース（1357）、ドル円、米10年債・2年債利回りと逆イールド判定、CNN Fear & Greed Index。これらはWebSearchでは取得できないか数日古い値しか得られない実績があるため、検索しない。スクリプトが「取得不可」を返した項目に限り、サブエージェントにWebSearchでのフォールバックを依頼してよい（その場合は値が数日古い可能性を明記する）。

### 手順2-2: 経済指標（サブエージェントがWebSearchで取得）
米雇用統計、FOMC（政策金利・声明要旨）、FOMCドットチャート、米GDP、CPI（総合・コア）、ジャクソンホール会議、ISM製造業・非製造業PMI、日銀短観、日経VI。詳細は `tools/データ収集指示.md` のタスクA。

### 手順2-3: 当日の相場天気予報からのキャッシュ再利用（時間短縮）
手順1で `$D/weather_cache.md`（当日の天気予報。Routine用ブランチ `claude/ecstatic-tesla-660dhs` から取り出したもの）が得られた場合、手順2-2のうち日経VI以外（月次・四半期発表で日中に変化しない項目）はその値を再利用してよい。再利用した項目は、手順3-1の「■取得データサマリー」において `（本日7:02取得のキャッシュを再利用）` のように**取得時刻とキャッシュである旨を必ず明記すること。**
- 手順2-1の項目と日経VI、手順3の全項目は再利用せず、必ず取り直す（手順1のスクリプトで毎回自動的に取り直される）。
- **天気予報に書かれたClaudeの相場観（「■Claudeの相場観」の節）は、再利用の対象外である。** 手順5-3のプロンプトへ混ぜてはならず、手順6の総合見解の前提としても使わない。プロンプトへ渡すのは数値・事実のみとする。

## 手順3: 銘柄ファンダメンタルズ・数値情報
値には取得日時を明記し、確認できなかった項目は推測で埋めず「取得不可」と明記すること。

**手順1のスクリプトで取得済み（検索しない）**: 現在値・始値・高値・安値・出来高、直近10営業日の日足、テクニカル指標、時価総額、実績PER、予想PER、アナリストのレーティング・目標株価、Yahoo表示の決算予定日。

**サブエージェントがWebSearchで取得**（詳細は `tools/データ収集指示.md` のタスクB）:
・企業概要
・直近決算（売上高・利益の成長率など）と次期ガイダンス
・過去8四半期（2年分）のBeat/Miss履歴（EPS・売上高・次期ガイダンス）。`Beat n回／Miss m回（対象n+m期）` の形で集計する。8期に満たない場合は取得できた期数を明記する
・次回決算発表予定日（公式発表で確認。BMO/AMC、本日からの日数も）。Yahooの表示は推定値のことがあり、2026-09-23にはYahooが11/06（推定）、WebSearchの報道が11/05と食い違った
・ニュース・アナリスト評価（格上げ・格下げ、目標株価変更）
・急騰・急落の背景ニュース（最重要）
  (a) `_data.txt` の「大きな値動き」に列挙された全日付の原因ニュース。画像を目で探す必要はない（銘柄のボラティリティに応じた閾値で機械的に抽出済み）。調査カテゴリには**指数の組入れ・除外（S&P500・S&P100・NASDAQ100・Russell等）**と**コーポレートアクション（株式分割・自社株買い・増資・M&A・スピンオフ・経営陣交代・ロックアップ解除・インサイダー売買）**を必ず含める（以前これを検索対象から漏らし、急騰の主因を特定できなかった実績がある）。
  (b) 直近10営業日のうち前日比±5%以上の全日について、日本語・英語＋日付指定の2種類以上で検索する。**「セクター高」「地合い」のような銘柄固有でない説明しか得られなかった場合は、それを結論として採用してはならない。** 再検索しても銘柄固有の材料が見つからない場合に限り、「銘柄固有の材料は特定できず（セクター全体の動きによる可能性）」と明記する。
  (c) チャート画像の最終日と直近取引日の突合: 画像は手順1で最新の日足から生成するため、画像の最終日は常に直近取引日と一致する。画像に写っていない期間の値動きは原理的に発生しない。
  (d) 今後予定されているイベント（指数組入れ・除外の実施日、決算発表日、ロックアップ解除日、投資家説明会等）を日付とあわせて記載する。特に指数組入れは、実施日を境に需給が一変するため必ず記載すること。

### 手順3-1: 取得データのユーザーへの表示（見落とし防止）
手順1〜3で取得した内容は、NotebookLMへ送るプロンプトに埋め込むだけでなく、見出し「■取得データサマリー」を付けて、後述の手順5-4（各ノートブックの回答表示）より前に、ユーザーへ提示すること。これは、ニュースや指標がプロンプト内に埋もれてユーザーの目に触れないまま処理が進むことを防ぐためである。取得できた値・日時・出典をすべて含め、取得不可の項目も「取得不可」と明記して残すこと。
- 表示の中身は、`macro.txt`、`econ_search.txt`、`_data.txt`、`fund_search.txt` の内容である。ただし `_data.txt` の「直近10営業日の日足」と「大きな値動き」の一覧は、表として並べ直さず「急騰・急落の背景」の各項目に日付と騰落率を添える形でよい（数値の重複表示を避けるため）。

### 手順3-2: 送信前の検証ゲート（重大な抜けの防止）
手順5-3で【送信プロンプト】をNotebookLMへ送信する**前に**、以下のチェックを必ず自分で行い、1つでも満たせない項目があれば送信せず、手順2・手順3に戻って追加調査すること。これは、著者ペルソナが不完全・誤った前提のまま投資判断を下すこと（過去に実際に発生した）を防ぐためのゲートである。

1. **直近の大きな値動きの原因を、銘柄固有の具体的な事実で説明できているか**: 直近5営業日以内に±5%以上の日次変動がある場合、その原因を「指数組入れ」「決算」「格上げ」等の固有名詞を伴う事実で説明できていること（サブエージェントの「チェック1」で確認）。
2. **チャート画像の最終日が直近取引日と一致しているか**: `_data.txt` の見出しの日付と「直近10営業日」の最終行で確認する。手順1のスクリプトを分析の直前に実行していれば常に満たされる。
3. **「現在値」がどの日付の終値（または取引時間中の暫定値）かを明記しているか**: `_data.txt` の「現在値」行に自動で明記される。
4. **手順2の全項目に値または「取得不可」が入っているか**: `macro.txt` とサブエージェントの「チェック4」で確認する。
5. **次回決算発表予定日と、本日からの日数が入っているか**（サブエージェントの「チェック5」）。
6. **今後予定されているイベント（指数組入れ実施日等）が判明していれば記載されているか**（サブエージェントの「チェック6」）。

このチェックの結果は、手順3-1の「■取得データサマリー」の末尾に `■送信前チェック: 1〜6すべて確認済み` の1行を付けてユーザーに示すこと。満たせなかった項目がある場合は、その番号と理由（追加調査しても取得できなかった旨）を明記すること。

## 手順4: 対象ノートブックの特定
`nlm notebook list` を実行する前に、必ず「補足: NotebookLM認証の更新」に従って手順Aを先に実行し、認証を更新すること。認証エラーが出るのを待ってから手順Aを実行するのではなく、**先に手順Aを済ませてから** `nlm notebook list` を叩く（NotebookLMのセッションCookieは分析依頼のたびに失効していることが多く、素で叩いて失敗するのを待つより、先に更新した方が速い）。既に認証が有効な場合でも、手順Aの再実行によるデメリットはない。
`nlm notebook list` を実行し、タイトルに「Claude」（大文字・小文字は問わない）を含むノートブックをすべて対象とする。対象ノートブックの一覧をコード側に固定せず、その時点で該当するものをすべて自動的に対象へ含めること。
手順0で「Claude_新高値ブレイク投資術」「Claude_株空売り 5つの戦術」の分析がNOと回答された場合、この2つを対象ノートブック一覧から除外する。YESの場合、または手順0自体が省略された場合は、通常通りこの2つも対象に含める。

## 手順5: 対象ノートブックへ一括送信する（`tools/run_notebooks.sh` による並列シェル実行）

**ノートブックごとにサブエージェント（Agentツール）を起動してはならない。** `nlm` コマンドを数本叩くだけの処理にサブエージェントを1件起動すると、起動時のシステムプロンプト読み込みと、ツール呼び出しのたびに発生する文脈の再読み込みで、1件あたり約57,000トークンを消費する（6件で約34万トークン。2026-09-22の実測値）。実際にメイン会話が必要としているのは各400字程度の回答本文だけであり、シェルで直接並列実行すれば同じ結果が約5,000トークンで得られる。手順2・3のデータ収集だけは、検索の生データが巨大なためサブエージェントへの委譲を維持する（上記「手順2〜3の実行方式」を参照）。

スクリプトは `nlm notebook list` のタイトルに「Claude」を含む全ノートブックを自動的に対象とし、全件を並列実行する。所要時間は最も遅い1件とほぼ同じになる。

### 5-1・5-2. 画像ソースの差し替え（データ収集の完了を待たずに先行実行する）
前回このワークフローで追加したチャート画像を、手順1で生成した画像へ入れ替える。テキスト・マニュアル等の画像以外のソースには触れない（スクリプトはTITLEが .png / .jpg / .jpeg で終わるソースのみを削除対象とする）。
```bash
tools/run_notebooks.sh --phase images --image "$D/<ティッカー>_chart.png" --image "$D/<ティッカー>_intraday.png" [--exclude '<除外する正規表現>']
```
手順0で2つのノートブックの分析がNOと回答された場合は `--exclude '新高値ブレイク投資術|株空売り'` のように渡して除外する。

### 5-3. プロンプトの組み立てと送信
`送信プロンプト雛形.txt` を一字一句改変せず使用する。差し込むデータは、手順1のスクリプト出力とサブエージェントの出力ファイルを `cat` で連結して作る。**Claudeが内容を書き写し直さないこと**（転記ミスの防止と、出力トークン・時間の節約のため）。雛形の他の文言は自動的に保持される。
```bash
cat "$D/<ティッカー>_data.txt" "$D/fund_search.txt" > "$D/fundamentals.txt"
cat "$D/macro.txt" "$D/econ_search.txt" > "$D/economic.txt"
tools/build_prompt.sh "$D/fundamentals.txt" "$D/economic.txt" "$D/prompt.txt"   # 12,000文字を超えるとエラーで止まる
tools/run_notebooks.sh --phase chat --prompt "$D/prompt.txt" --out "$D/out" [--exclude '<除外する正規表現>']
```
`--exclude` には 5-1・5-2 と同じ値を渡すこと。

**NotebookLMのチャット入力は約12,000〜14,000文字を超えると、エラーではなく空応答になる**（2026-09-23実測。MUのプロンプト15,947文字で5冊すべてが失敗した）。`build_prompt.sh` が12,000文字超でエラー終了した場合は、Claudeが書き写して縮めるのではなく、サブエージェントにSendMessageで「出典と経緯説明を削った短縮版を書き直す」よう依頼し、その短縮版で組み立て直すこと。

所要時間の目安: 全件並列のため、6冊でも1分前後で完了する。

会話履歴について: スクリプトは常に `nlm generate-chat --web` で送信する。`--web` はサーバー側の会話を使うため、やり取りがNotebookLMの画面に履歴として残り、ユーザーが後からUI上で追加の依頼（図解画像の生成など）をできる。**`--web` を外すと generate-chat は one-shot 扱いとなり、手元にしか残らずNotebookLMの画面には履歴が一切現れないので、絶対に外さないこと**（2026-09-22に実際に発生し、ユーザーがUIで「直前の判定を図解して」と依頼しても参照先が存在しない状態になっていた）。
なお履歴はノートブックごとに1本の会話へ**追記されていく**ため、別銘柄の分析を重ねると過去の銘柄のやり取りも同じ会話に残る。

**`nlm chat delete <notebook-id>` は使わないこと。** 「Chat history deleted.」と成功を返すが、実際には`--web`で作られた保存済み会話は削除されない（2026-09-22に検証済み: 削除実行の直後に生のAPIレスポンスを直接確認したところ、内容がタイムスタンプも含めてそのままサーバーに残っていた）。このRPCは「現在のデフォルトチャット」をクリアするだけで、`--web`が使う保存済み会話オブジェクトには効かないとみられる。著者が過去の銘柄に引きずられる懸念が出た場合や、履歴を消したい場合は、**ユーザー自身にNotebookLMのUIでチャットパネルから手動削除するよう案内すること。** Claude側でCLIから削除を試みてはならない。

重要な注意事項（過去に間違えた点）:
- 「投資判断マニュアル」の内容を、Claude自身が独自に抜粋・要約してプロンプトに埋め込んではいけない。マニュアルは各ノートブック内の既存ソースに含まれているので、NotebookLM自身にそのソースを参照・適用させること。
- プロンプトに「マニュアルをここに貼り付ける」といった加工は行わず、`送信プロンプト雛形.txt` をそのまま使うこと。雛形を編集してよいのは `{{FUNDAMENTALS}}` と `{{ECONOMIC_DATA}}` の差し込みのみで、これは `tools/build_prompt.sh` が行う。
- スクリプトが内部で使う `--citations off` は、文末の引用元リスト（出典番号・ソースファイル名・確信度等の一覧）の出力を抑制するオプションであり、回答本文の内容・意味を変更するものではない。

### 5-4. 結果の表示
NotebookLMから返ってきた回答を、要約・省略・言い換えを一切せず、全文そのまま（チェックリスト照合結果や表も含めて）表示すること。表示の先頭には見出し「■ノートブック：〈ノートブック名〉」を付け、どのノートブックの回答かを明示すること。Claudeが自分の言葉でまとめ直してはいけない。

## 手順6: すべてのノートブックの結果を表示した後、Claudeとしての総合見解を提示する
対象ノートブックすべての回答（手順0でNOと回答され除外されたノートブックがあれば、それは含まない）が出揃ったら、最後に見出し「■Claudeの総合見解」を付けて、以下を提示すること。
・各ノートブックの投資判断（買い／売り／様子見）が一致しているか、割れているか
・割れている場合、情報源の違い（書籍本文、YouTube由来、他の関連書籍など）から考えられる理由
・それらを踏まえた、Claude自身の言葉による総合的な所見（現時点で買い・売り・様子見のどれに近いか、特に注視すべき懸念点やリスク）
・もしエントリーする場合の価格を、買い（ロング）・空売り（ショート）の両方について提示すること。それぞれ「エントリー価格」「利益確定（利確）価格」「損切り価格」の3点を具体的な数値で明記し、あわせて現在値からの騰落率（現在値比 ±○○.○%）を併記する（計算式: （各価格 − 現在値） ÷ 現在値 × 100、小数第1位まで）。基準とした現在値も明記すること。各ノートブックの回答内で言及されているエントリー値・損切り値・利確目標を踏まえつつ、Claude自身の言葉で買いシナリオ・空売りシナリオそれぞれとして整理し直すこと。現時点でどちらの方向にもエントリー条件が整っていない（様子見）場合であっても、「条件が整った場合に想定される価格帯」として買い・空売り双方を省略せず必ず記述すること。
・**あわせて、買い・空売りそれぞれについて「本日の成行判断」と「翌営業日の予約注文」を必ず分けて記述すること。** 「様子見」で終わらせると、ユーザーは引け後に注文をセットできず、翌日の寄り付きでシグナルが出ても取り逃す（実際にこの時差が発生した）。各ノートブックが手順5-4の「現状パターン」でA／B／Cのどれを選び、どの価格を予約注文・押し目監視価格として挙げたかを踏まえ、次の2行を加えること。
  - `本日の成行判断: 〈エントリー可／見送り（理由を数語）〉`
  - `翌営業日の予約注文: 〈注文種別〉○○○（現在値比 ±○○.○%）／発動条件: 〈条件を数語〉`（パターンCで押し目待ちの場合は `押し目監視価格` として記載する）
  なお「今この価格で成行注文を出すこと」と「条件成立時に発動する予約注文を引け後にセットしておくこと」は別の行為であり、後者は予測による先回りエントリーには当たらない（条件が成立しなければ約定しないため）。この区別を崩してはならない。
・**Claudeの総合判断も「注文を発注するか否か」で決めること。** 予約注文をセットすべき局面は『様子見』ではなく『買い（予約）』『売り（予約）』とする。注文を一切出さず条件の再形成を待つだけの場合のみ『様子見』とする。各ノートブックの判定を集計する際も、この基準で揃えること。
・**各ノートブックが判定を下した軸（テクニカル／ファンダメンタルズ）を区別して記述すること。** 本ワークフローの判定対象は `投資憲法.md` 第1条の通りスイングトレード（想定保有期間1日〜1ヶ月）であり、テクニカル要因が主たる判断軸となる。ある著者がファンダメンタルズ要因（PER・決算Beat履歴等）を理由に様子見としている場合は、それが当該著者のマニュアルで明示的にエントリー条件とされているものか、それとも保有期間のより長い判断軸によるものかを明記し、スイング判断としての妥当性を読み手が判断できるようにすること。
この総合見解は各ノートブックの回答を要約したものではなく、複数ノートブックを横断して比較したうえでのClaude独自の評価として記述すること。

### 手順6-2: 投資憲法に基づく数値算出（■リスク管理数値）
「■Claudeの総合見解」を提示した直後に、続けて見出し「■リスク管理数値」を付けて、`投資憲法.md` 第3条のルールに基づく**3つの数値のみ**を提示すること。

条項ごとの適合／違反の照合表および総合判定（GO／STOP）は**廃止した**。毎回ほぼ同じ内容（全ノートブックが様子見である限り常にSTOP）となり冗長なため、実際に売買判断へ使える数値だけを残す方針に変更している。

提示するのは以下の3行のみ:
1. `損切り中央値: ○○○（対象n冊）` — 手順5-4で各ノートブックが提示した損切り値の中央値。偶数件の場合は中央2件の平均。損切り値を提示しなかったノートブックは集計から除外する。
2. `利確中央値: ○○○（対象n冊）` — 同様に利確目標の中央値。複数目標を提示したノートブックは最終目標値を採用する。
3. `ポジション上限: ○○%（損切り幅○○%、買い／空売りそれぞれ）` — 手順6で提示した買い・空売りシナリオの損切り幅から、第3条の計算式 `min( 2% ÷ 損切り幅 , 15% )` で算出する。

注意点:
- **Claudeが投資憲法の内容を推測・補完してはいけない。** 第3条の計算ルールが変更されている場合は、変更後のルールに従うこと。
- `投資憲法.md` が存在しない場合、または第3条の損切り・利確・ポジションサイジングのルールが `【要記入】` のままの場合は、算出を行わず次の1行のみを表示する:
  「■リスク管理数値: 投資憲法の第3条が未記入のため算出できません。」

## 補足: NotebookLM認証（NLM_AUTH_TOKEN / NLM_COOKIES）の更新
手順4の直前に、認証エラーの有無を問わず毎回この手順Aを先に実行すること（詳細は手順4を参照）。`nlm` コマンドが「authentication expired or invalid」等のエラーを実際に返した場合も同様に、まず以下の手順A（PC不要・VPS経由）を試すこと。手順Aが使えない場合（環境変数`NLM_VPS_CDP_BASE`が未設定、またはVPS自体が停止している等）のみ、手順B（PC必須）をユーザーに依頼する。

### 手順A: VPS経由での自動再認証（PC不要、Claude自身で実行可能）
環境変数 `NLM_VPS_CDP_BASE`（例: `wss://nlm-server-8823.com:443/nlmcdp-<秘密トークン>`）が設定されている場合、以下をClaude自身が実行してよい。

**重要（過去に間違えた点）**: 接続先は必ず `$NLM_VPS_CDP_BASE` に入っているドメイン名（`nlm-server-8823.com`）をそのまま使うこと。VPSのIPアドレス（`34.133.108.107`等、NOTEBOOKLM_SETUP.mdに記載）を直接使ったり、`/json/version`のレスポンスに含まれる`webSocketDebuggerUrl`のホスト部分（`127.0.0.1`になっている）をそのまま流用したりしては絶対にいけない。ドメイン宛のTLS証明書を使っているため、IPアドレスやドメイン以外のホスト名で接続するとTLS証明書検証エラーで必ず失敗する。UUID（`/devtools/browser/`の後ろの部分）だけを取り出し、それ以外は`$NLM_VPS_CDP_BASE`の文字列をそのまま使うこと。

1. 現在のChromeのUUIDを取得し、`$NLM_VPS_CDP_BASE`と組み合わせて接続先URLを機械的に組み立てる（以下をそのままコピーして実行してよい。手で書き換えない）。
   ```bash
   HTTP_BASE="${NLM_VPS_CDP_BASE/wss:/https:}"
   UUID=$(curl -sS "$HTTP_BASE/json/version" | grep -oE '/devtools/browser/[a-f0-9-]+' | head -1 | sed 's#/devtools/browser/##')
   CDP_URL="${NLM_VPS_CDP_BASE}/devtools/browser/${UUID}"
   echo "$CDP_URL"   # ドメイン名(nlm-server-8823.com)になっているか必ず目視確認してからnlmに渡すこと
   ```
2. `echo`で表示された`$CDP_URL`にIPアドレスが含まれていないこと（ドメイン名になっていること）を確認した上で、パッチ版 `nlm`（session-start.shが自動ビルド済み）で再認証する。
   ```bash
   nlm auth -cdp-url "$CDP_URL"
   ```
3. **成功しても認証情報は現在のシェルに自動で反映されない。** `nlm auth` は `/root/.nlm/env` へ書き出すだけであり、これを読み込まずに `nlm notebook list` を叩くと「no valid profiles found」で失敗する（2026-09-22に実際に発生）。`nlm` を直接実行する場合は、同じコマンド内で必ず先に読み込むこと。
   ```bash
   set -a; source /root/.nlm/env; set +a
   nlm notebook list
   ```
   なお `tools/run_notebooks.sh` と `tools/build_prompt.sh` はこの読み込みを内部で行うため、スクリプト経由なら意識しなくてよい。
4. もし手順2が「redirected to authentication page」「detected sign-in page」等、Googleセッション自体が切れていることを示すエラーになった場合は、VM上のChrome自体への再ログインが必要（手順Aでは解決できない）。ユーザーに、ブラウザで `http://34.133.108.107:6080/vnc.html`（VMのnoVNC、事前にVM側で `x11vnc`/`websockify` が起動している必要あり）を開いてNotebookLM専用サブアカウントに再ログインするよう依頼し、ログイン完了の報告を受けてから手順1に戻ること。これは携帯のブラウザからでも操作可能なので、PCは不要。

### 手順B: PC経由での再認証（手順Aが使えない場合のみ）
1. PCでChromeを完全終了し、`--remote-debugging-port=9222 --user-data-dir="C:\chrome-nlm-debug"` 付きで起動
2. NotebookLM専用サブアカウントで再ログインし、https://notebook.google.com を開く
3. `nlm auth -cdp-url ws://localhost:9222` で再認証
4. `nlm auth --print-env` で表示された値（クォート文字は含めない）を、claude.ai/codeの環境「分析」の環境変数欄に `NLM_AUTH_TOKEN=...` / `NLM_COOKIES=...` として貼り付け・保存
5. 保存後、間を空けずに新しいセッションで分析を再実行する
